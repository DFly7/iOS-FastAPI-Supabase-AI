Before → After: key improvements
v1 — before

Only GET endpoints. No mutation example. Placeholder repo/service with no real impl. ContentView calling API directly. No error or loading states. Single-screen with one call.

v2 — now

Full CRUD: GET (list + single), POST (201), PATCH (both profile + notes), DELETE (204). Real repo + service layers. @Observable ViewModel. Per-call loading, error banners with retry.

v1 — before

New strengths

"Services orchestrate one or more repositories and contain business logic. Keep repository calls here so routers stay thin (validate input → call service → return schema)." This one-liner teaches the pattern without over-engineering it.

NoteOut+Identifiable.swift — the right place to extend generated models
Extending generated code in a separate file instead of editing the generated file is exactly right. The comment explains why. This is the kind of micro-convention a template should model.

The _SELECT = "id, user_id, title, body, created_at, updated_at" constant avoids column drift. Every mutating query also guards on user_id alongside the RLS policy — defense-in-depth that's worth copying.

AuthService: userFacingMessage error mapping
Maps Supabase SDK raw error strings to user-friendly copy. Handles Apple Sign In cancellation, URLError network codes, and a comprehensive set of Supabase auth error substrings. This function alone saves hours when building a real app.

Skeleton Code Conventions
The patterns in the skeleton code are now genuinely good. Here's what's excellent and what's still worth polishing.
Python / FastAPI — what's excellent
Feature sub-router pattern is demonstrated live
Notes router lives in api/v1/notes.py, imported and included in the main router. The commented example at the bottom (# from app.api.v1.invoices import router as invoices_router) shows exactly how to add the next one. This was the key structural gap in v1.
strength
Status codes used correctly: 201 on POST, 204 on DELETE
status_code=status.HTTP_201_CREATED on create, HTTP_204_NO_CONTENT on delete, explicit 404 raises in both single-resource endpoints. Many templates get this wrong by returning 200 everywhere.
strength
NoteIn validates fields at the schema layer
title: str = Field(..., min_length=1, max_length=255) — FastAPI returns 422 automatically if validation fails, with a structured error body. The DB has a matching check (char_length(title) between 1 and 255). Defense at both layers.
strength
PATCH semantics done correctly in both profile and notes
model_dump(exclude_none=True) means only explicitly provided fields are sent to the DB. Profile additionally rejects an empty body with 422. Notes handles the no-change case by returning the existing row. Correct PATCH semantics throughout.
strength
Python — nuances worth knowing
All route handlers are def not async def
The Supabase Python client is synchronous, so sync handlers are correct and avoid FastAPI running them in a thread pool. But the template doesn't show any async I/O pattern. When a user adds an httpx call or a second async client, they won't know to use async def. A brief note in the router or README would help.
note
Router has mixed inline routes + included sub-router
Notes is a proper sub-router in its own file. Profile GET + PATCH are inline in router.py. This isn't wrong — showing both patterns is educational — but a new contributor might not know which convention to follow when adding feature #2. A brief comment like "prefer feature sub-routers for non-trivial routes" would guide the decision.
clarity
iOS / Swift — what's excellent
@Observable ContentViewModel with correct @State ownership
@State private var viewModel = ContentViewModel() — using @State with @Observable is the iOS 17 way. ViewModels don't need to be ObservableObject anymore. Every property is tracked granularly.
strength
ObservableObject for AuthService is still correct
AuthService uses ObservableObject (old pattern) because it's injected as @EnvironmentObject which still requires it. Using @Observable for a service shared via environment would require different injection. This mixing is correct, not inconsistent.
strength
UI-only state stays in the View, not the ViewModel
The comment "Local UI-only state — purely presentational, not part of the model" in ContentView.swift is correct. isEditingDisplayName, isShowingNoteComposer etc. are view concerns. ViewModel owns async state. The separation is principled and annotated.
strength
BackendAPIService has proper error type + shared codecs
ServiceError: LocalizedError with noAccessToken and unexpectedStatus(Int, String?). Shared decoder/encoder singletons with ISO 8601 dates. The request() core helper eliminates code duplication across all endpoints.
strength
iOS — minor remaining gaps
accessToken passed to every ViewModel method as a parameter
Every viewModel.fetchNotes(accessToken: authService.accessToken) passes the token explicitly. This is clear and decoupled — but it means every new ViewModel method needs the parameter. An alternative would be to inject AuthService into the ViewModel at init. Both are valid; the current approach is arguably simpler for a template.
pattern
ContentView.swift is 318 lines and growing
Within SwiftLint's file_length warning (600) but the trend is clear — each new feature adds ~60 lines. The view is doing secure test + profile + notes. When a third data entity arrives it'll push 400+. Splitting into NotesSection.swift and ProfileSection.swift as separate view structs would model the right habit.
future

CI / CD
The CI pipeline is now genuinely good. The lint-first pattern, coverage reporting, and dynamic UDID are all production-grade.
What's excellent now
backend-ci.yml

lint → test → check-models → docker

Proper dependency chain. needs: lint on test job. needs: test on both check-models and docker-build. Lint failure blocks tests. Test failure blocks Docker push. Exactly right.

Coverage

GitHub Step Summary

Coverage report written to $GITHUB_STEP_SUMMARY as a markdown code block. Visible on every CI run in GitHub Actions UI without needing a third-party service. Elegant.

ios-ci.yml

Dynamic UDID via Python JSON

Resolves iPhone 16 UDID by querying xcrun simctl list and sorting by runtime version. Picks the newest iOS. Much more robust than a hardcoded UDID.

All workflows

Concurrency + Docker GHA cache

Every workflow has a concurrency: key with cancel-in-progress. Docker uses cache-from/to: type=gha,mode=max. These are the two easiest wins that most CI setups miss.

Remaining gaps
SwiftLint installed via brew install on every run
No cache for the SwiftLint binary. Each iOS CI run spends ~40–60s on brew install swiftlint. Fix: use actions/cache@v4 to cache the Homebrew install dir, or use the norio-nomura/action-swiftlint or realm/SwiftLint actions which handle their own install.
perf
No timeout-minutes on iOS CI job
backend-integration.yml has timeout-minutes: 15. The iOS build job on macos-15 doesn't. Xcode builds can hang silently (e.g. waiting for a simulator to boot). A 30-minute timeout would prevent wasted runner minutes.
reliability
xcpretty installed via gem install on every run
Similar to SwiftLint — gem install xcpretty --no-document isn't cached. The macos-15 runner might have it pre-installed (check with which xcpretty), which would make this a no-op. Worth verifying and either caching or removing the install step.
optimise
No UI test step in iOS CI
ios-ci.yml runs -only-testing:StarterAppTests (unit tests). UI tests (StarterAppUITests) are scaffolded but not executed in CI. This is fine for now — UI tests are slow and require more setup — but worth noting as a future addition.
future
SwiftLint caching fix
# ios-ci.yml — cache SwiftLint binary
- name: Cache SwiftLint
  uses: actions/cache@v4
  with:
    path: /opt/homebrew/bin/swiftlint
    key: swiftlint-${{ runner.os }}-${{ hashFiles('.swiftlint.yml') }}

- name: Install SwiftLint (if not cached)
  run: which swiftlint || brew install swiftlint

Blueprint: what to build
Priority 1

.cursor/rules/

project-context.mdc (always-attach: true), python-backend.mdc, ios-swift.mdc, database.mdc. Each rule encodes what an agent needs to know for that layer.

Priority 2

AGENTS.md

Root-level context file. Include: stack diagram, make dev and other key commands, how to add a feature (the 8-step chain), file naming conventions.

Priority 3

.agent/mcp.json

Supabase MCP for DB queries + migration runs. Filesystem MCP for structured file reads. Config pointing to local Supabase instance or hosted project.

Priority 4

.agent/skills/

add-feature.md — the 8-step chain from schema to iOS service. add-migration.md — naming, RLS, triggers. sync-models.md — when and how to regenerate.

Priority 5

scripts/status.sh --json

Structured JSON output: Supabase running/stopped, backend URL, migration count, last migration name. An agent runs this to understand current state before acting.

Priority 6

make agent-setup

Installs MCP dependencies, links .agent/mcp.json to the Cursor project config path, validates Supabase connectivity. One command to go from clone to agent-ready.

# iOS · FastAPI · Supabase Starter
Stack: SwiftUI (iOS 17+) · FastAPI (Python 3.12, uv) · Supabase (Postgres 17)
Monorepo layout: ios/ · backend/ · supabase/migrations/ · scripts/

## Key commands (run from repo root)
make dev                         # Full stack: Supabase + Docker + Simulator
make dev ARGS=--no-ios           # Services only (backend + Supabase)
make sync-models                 # Regenerate GeneratedModels.swift from Pydantic
make ios-gen                     # Regenerate Xcode project (Tuist)
cd backend && uv run pytest      # Unit tests

## Adding a feature (8-step chain)
1. backend/app/schemas/<feature>.py      → Pydantic In/Out/Update models
2. backend/app/repositories/<feature>_repo.py → DB queries (accept Client)
3. backend/app/services/<feature>_service.py  → Business logic
4. backend/app/api/v1/<feature>.py        → Router, include in router.py
5. supabase/migrations/YYYYMMDDHHMMSS_add_<feature>.sql → RLS + indexes
6. make sync-models               → updates GeneratedModels.swift
7. ios/…/Services/BackendAPIService.swift → Add endpoint methods
8. ios/…/ViewModels/ContentViewModel.swift → Add state + actions
