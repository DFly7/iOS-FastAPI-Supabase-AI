01 Template usability

Can someone clone the repo and ship? What is the lowest-friction path?

What works well

The canonical path is clear: root make dev runs scripts/dev.sh, which orchestrates Supabase, backend (Docker), env and xcconfig, Tuist install/generate, and the Simulator. Tool versions are pinned in .mise.toml (Python, uv, Tuist, SwiftLint, Supabase CLI). README matches this flow and documents architecture, CI entry points, and the repo tree.

iOS uses Tuist as the single source of truth (Project.swift); the Xcode project is generated, which avoids drift—at the cost of one extra step after clone (tuist install / tuist generate, mirrored in CI and Makefile targets like ios-gen).

Friction for new users

  • Must install mise (or equivalent) and Docker; physical-device testing still expects tunnel literacy.
  • local-setup.md references run.sh / build-run.sh that are not in the repo—README and make dev are the truth.
  • Linux contributors: scripts/_lib.sh uses BSD sed -i ''.

Verdict

Run with it For a team already using Mac + Xcode, this is highly usable: one command brings up the full stack. Fix doc drift and you remove the main footgun for newcomers and agents alike.

02 Path to the App Store

TestFlight automation, signing, and what is still manual.

Strengths

  • distribution-setup.md + scripts/setup-dist.sh: wizard for Team ID, App Store Connect API key, Match repo, and GitHub secrets checklist.
  • Fastlane: beta lane (Match readonly CI, gym, TestFlight upload); release lane for App Store upload (submit for review left off by default).
  • .github/workflows/distribute.yml: triggered by v* tags or manual dispatch; Release xcconfig from secrets; Tuist + Fastlane aligned with iOS CI Xcode/mise versions.
  • Project.swift sets ITSAppUsesNonExemptEncryption with an accurate comment for standard TLS-only apps; ATS allows local networking for dev.
  • Sign in with Apple entitlements are present; deep link scheme tracks bundle identifier.

Gaps and caveats

  • CI drives TestFlight; a dedicated “submit to App Store review” workflow is not the focus—teams use the release lane locally or extend Actions.
  • Release workflow must align BACKEND_URL and real hosting; placeholder patterns require explicit replacement.
  • Fresh fork needs real bundle ID, secrets, Match seeding, and production Supabase/PostHog values—expected for a template, but not “zero-config App Store.”
  • iOS CI runs unit tests only (-only-testing:StarterAppTests); UI tests are scaffolded but not in CI.

03 Skeleton code conventions

Are patterns consistent and teachable?

Overall: yes—modern SwiftUI with clear seams

  • Strict concurrency: Tuist base settings push toward safe defaults (SWIFT_DEFAULT_ACTOR_ISOLATION / MainActor story per project).
  • MV-style: @Observable view models (e.g. ContentViewModel) separated from views for previews and tests—good teaching shape.
  • Networking: BackendAPIService as a static enum with shared JSON codecs aligned to FastAPI; simple and readable; tradeoff is heavier mocking without URLProtocol/protocol injection.
  • Config: APIConfig reads Info.plist populated from xcconfig—no secrets in source; fails fast if keys missing (opinionated; acceptable for a starter).
  • Generated boundary: GeneratedModels.swift excluded from SwiftLint; backend CI checks model sync—excellent convention for agents (“don’t hand-edit generated files”).
  • Tests: Swift Testing for units; XCTest UI scaffold—conventions are current Apple ecosystem practice.

04 Developer experience (full repo)

Backend, Supabase, and CI—what makes day two pleasant?

Highlights

  • FastAPI app is well-layered: settings via pydantic-settings, JWKS verification, RLS-aware Supabase clients, rate limits, optional Sentry/Prometheus, documented middleware order.
  • Integration tests use real local Supabase; unit tests avoid integration marker—workflow split is documented.
  • Migrations + RLS in SQL are a strong reference (profiles trigger, notes table pattern).
  • Backend CI: Ruff, mypy, pytest, Docker build, optional GHCR push gated by repo variable.

Friction

  • No root make backend-test / make lint—developers must cd backend and use uv commands.
  • Integration workflow runs on main (not every PR) by design—worth stating loudly for contributors.
  • AuthContextMiddleware decodes JWT for logging only; real auth stays on verify_jwt—document so no one misuses request state as authorization.

05 Agent X readiness

Your next step: skills, .agent/, MCP, CLIs. Today the code is agent-friendly; the contract for agents is mostly missing.

Current state

There is no AGENTS.md, no .agent/ playbooks, no bundled Cursor rules that encode Tuist/generated-file boundaries, and no single “command matrix” that mirrors CI. An autonomous agent can succeed by reading README and workflows—but success rate jumps with an explicit layer.

Artifact Purpose
AGENTS.md One page: stack map, forbidden paths (generated Xcode, xcconfig secrets), exact commands for dev/test/sync-models/distribute, PR vs main test behavior.
.agent/context.md Ports, auth flow diagram, RLS summary, where JWT is verified vs logged only.
.agent/skills Repeatable workflows: add backend route, add migration, add iOS screen, regen Tuist, fix model drift.
MCP Supabase MCP for schema/migrations; optional GitHub Actions status; keep tool schemas versioned beside the repo.
CLIs Expose make targets (or a thin wrapper script) so agents never guess uv run pytest -m "not integration" vs integration.

Why the skeleton already helps agents

Predictable directories (Services/, ViewModels/, api/v1/, repositories/), generated models with CI enforcement, and Makefile entry points are exactly the kind of structure models exploit—once documented.

06 Prioritized improvements

Beyond your roadmap—quick wins.

  • P0 Align docs: Update local-setup.md (and notes/makefile.md if kept) to reference make dev / scripts/dev.sh only.
  • P1 Root Makefile: backend-test, backend-lint, optional test-all that match CI.
  • P1 SwiftLint comment: CI uses mise; comment in .swiftlint.yml mentioning Homebrew is stale.
  • P1 UI tests: Either run a minimal UI test job on a schedule/main-only, or document omission explicitly in README.
  • P2 Networking testability: Introduce a protocol/abstraction around HTTP if you want richer mocked tests without refactors later.
  • P2 Portable sed: Consider a small helper for in-place file edits in _lib.sh.
Resend note (already vs wanted)
README already lists a Resend helper on the backend for transactional email. Your idea—Supabase auth confirmation emails via Resend—typically means either Supabase SMTP/custom SMTP configuration pointing at Resend, Auth hooks + Edge Functions, or custom confirmation flows through your FastAPI layer. The template gives you Resend on the API side; the remaining work is product-specific wiring to Auth’s lifecycle.
